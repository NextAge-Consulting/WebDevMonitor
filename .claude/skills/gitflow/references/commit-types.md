# Conventional Commit Types

Commit Format: `<emoji> <type>: <description>`

## Types

| Emoji | Type | Use For |
|-------|------|---------|
| ✨ | feat | New feature, new capability, new UI |
| 🐛 | fix | Bug fix |
| 📚 | docs | Documentation |
| 🎨 | style | Formatting, whitespace, naming (no behavior change) |
| ♻️ | refactor | Restructuring without behavior change |
| ⚡ | perf | Performance improvement |
| 🧪 | test | Test additions or changes |
| 🔧 | chore | Maintenance, deps, internal tooling |
| 🏗️ | build | Build system, bundler, or dependency manifest changes |
| 👷 | ci | CI/CD workflow changes (`.github/workflows/*`, CI configs) |
| ⏪ | revert | Reverting a prior commit |
| 🔖 | wip | Work-in-progress checkpoint (auto-formatted by `/checkpoint`) |
| 🚀 | release | Release PR — bump + changelog + tag + deploy (auto-formatted by `/deploy`) |

## Best Practices

- Present tense imperative mood ("add feature" not "added feature")
- First line under 72 characters
- Commit ALL changes together (never partial)
- Subject line summarizes; body (if needed) explains why

## Breaking changes

For breaking changes, include `BREAKING CHANGE:` footer or `!` after type:

```
✨ feat!: restructure user API
```

or

```
✨ feat: restructure user API

BREAKING CHANGE: UserProfile endpoint renamed from /user to /users/:id
```

This triggers a major version bump at `/deploy` time.

## Multiple Features in One Commit

Use multi-line message with primary type on first line and bullets in the body:

```
✨ feat: add feature A and feature B

- Feature A: description
- Feature B: description
- Fix: related fix description
```

Primary emoji/type should reflect the most significant change.

## Usage by gitflow scripts

- `commit.sh` takes `--message "<full message>"` and passes it verbatim to `git commit -m`.
- `checkpoint.sh` auto-formats as `🔖 wip: <timestamp> [optional suffix]`. These stay local: `commit.sh` and `ship-main.sh` fold them before pushing, so the type never reaches `main`.
- `deploy.sh` auto-formats the release PR title + squash commit as `🚀 release: v<X.Y.Z>`. The exact subject `^🚀 release: v\d+\.\d+\.\d+$` is the trigger pattern that release-aware CI workflows (`ci.yml`, `commitlint.yml`) detect to short-circuit heavy checks — the bump diff has already passed CI on the feature PRs that landed on main; re-running the full suite on the release PR is pure wait. Do NOT use this type by hand.
- PR titles (generated by Claude during `/open-pr`) follow the same format; the `commitlint.yml` CI check enforces this.
